# Authenticated webapp and optional Tailscale Funnel

The local webapp is included in the main Compose deployment. It uses native
Hermes username/password login
and binds only to host loopback. Funnel optionally publishes the same webapp
through public HTTPS. No Tailscale account is needed to visit a Funnel endpoint;
the visitor authenticates with Hermes. Native password authentication is intended
upstream for trusted networks/VPN use. Public exposure also exposes the native
login and session implementation to Internet traffic.

## First-run localhost access

Run `make init` and edit the root `.env` explicitly (initialization never adds
settings to an existing file):

```dotenv
WEBAPP_BIND=127.0.0.1
WEBAPP_PORT=9120
WEBAPP_USERNAME=admin
TAILSCALE_FUNNEL_ENABLED=false
```

`make init` generates missing credentials and renders proxy configuration.
`make webapp-credentials` and explicit `make webapp-rotate` operate on credential
files alone, so unrelated invalid deployment settings do not block login repair. Then
build and start the services:

```sh
make build
make up
```

Open `http://127.0.0.1:9120` or `http://localhost:9120`. Read the generated password
locally from `config/webapp/password`. The generator never prints it. The password
file and `config/webapp/auth.json` have mode 0600; auth.json contains the scrypt
hash and persistent random signing secret. Repeating `make init`
preserves matching credentials. Files are published atomically, with the saved
password written before its hash. A retry reuses that password if initial
creation stopped before authentication was saved. If the saved password and
hash disagree, initialization updates the hash to the saved password while
preserving the signing secret. If an explicit rotation was interrupted, rerun
`make webapp-rotate` to complete rotation of both password and signing secret.
A missing password cannot be recovered from its hash: restore it from backup or
run `make webapp-rotate` deliberately if you do not know it. Existing authentication
remains usable; initialization reports the missing saved password without blocking
startup or silently replacing the authentication identity.
`make init` does not start containers or initialize
wallets. Container-side `setup init` installs the settings when the stack starts.

The root `.env` supplies deployment settings. `config/webapp/proxy.cfg` is
generated by `make init` and regenerated on `make up`; edit `.env` or the
component renderer rather than treating the generated proxy file as authoritative. Generated credentials live under
`config/webapp/`, outside Git and Docker build contexts. Only the existing networkless
`setup` container mounts that directory read-only. It writes the native authentication settings
into the `hermes-data` named volume; neither the executor nor Tailscale receives
the webapp credentials. Protect backups of `config/` and Hermes state as secrets.

`make up` starts Hermes and the local webapp automatically. It reapplies
authentication/proxy settings and recreates the gateway so changes take effect.
Use `make down` before rebuilding/changing namespace configuration on an active
stack. Hermes state remains in its named volume; other persistent files remain
in separate directories under `data/`.

Use the deployment-aware Compose wrapper for other operator commands:

```sh
python3 scripts/stack.py compose logs -f hermes webapp-proxy
make chat
python3 scripts/stack.py compose exec teep curl -fsS http://127.0.0.1:8337/v1/models
```

This selects the same overlays as `.env`. Bare base-only Compose commands can
otherwise recreate services without their optional networks. Use `make up` and
`make down` for applying feature changes and shutdown.

## Optional public Funnel

Create a legitimate Tailscale enrollment key and permit Funnel for the node in
your tailnet policy. Set these additional root `.env` settings:

```dotenv
TAILSCALE_FUNNEL_ENABLED=true
TAILSCALE_HOSTNAME=private-hermes
TAILSCALE_FUNNEL_HOST=private-hermes.your-tailnet.ts.net
TAILSCALE_FUNNEL_PORT=443
TS_AUTHKEY=your-enrollment-key
```

The hostname is an example: supply your node's exact assigned `.ts.net` name.
Ports 443, 8443, and 10000 are supported by Tailscale Funnel. With a nondefault
HTTPS port, include it in the browser URL. Then run `make build` and `make up`.
Only this explicit activation starts the Tailscale container and enrollment.
Building images and running automated tests do not enroll or publish a node.

Tailscale starts with empty forwarding configuration. The wrapper waits for a
running authenticated node, checks that its DNS name exactly matches the configured
host, then publishes the fixed webapp target. A name mismatch fails closed.
Credentials and node identity persist in `data/tailscale/`;
TS_AUTHKEY can be removed after successful enrollment. An unenrolled node requires
the key. No host networking, TUN device, network capabilities, or Docker socket
is used; Tailscale runs with userspace networking.

Set `TAILSCALE_FUNNEL_ENABLED=false` and run `make up` to disable public ingress
while retaining local access. The workflow resets active Funnel configuration,
stops/removes the Tailscale container, and retains node state.
Shutdown also attempts reset. If reset cannot be confirmed, the workflow stops
the node and reports failure; the next start always begins with empty forwarding
configuration. `make down` remains available even after malformed feature settings
and shuts down the whole deployment without deleting persistent data.

Local web access is part of the base stack; there is no separate enable flag
or webapp overlay. Use `make down` to stop the deployment without deleting state.

## Authentication, origins, and authority

The native provider uses scrypt password hashes, 12-hour access tokens, and
30-day refresh tokens. The refresh token permits renewal after access-token
expiry. Its tokens are stateless: clearing browser cookies is not proof that
all captured tokens have been revoked. Rotate both the password and signing key
to invalidate outstanding provider tokens:

```sh
make webapp-rotate
make up
```

This saves a new password in the same private file and applies the new credentials
when the gateway is recreated. HTTP and HTTPS sessions use separate cookie names;
HTTPS cookies have the native Secure prefix/flag. Cookies are HttpOnly and
SameSite=Lax. Each hostname requires its own login.

HAProxy directly publishes the selected host loopback port and accepts Funnel
on a separate isolated network/listener. No publisher or forwarding containers
are needed. Hermes remains attached only to its isolated backend; the executor
is attached to neither ingress network.

At startup the proxy installs default-deny IPv4/IPv6 firewall rules. It accepts
local connections on the host-publication interface (on rootless Podman, from
the port forwarder over loopback; see [engine differences](architecture.md#rootless-podman))
and Funnel connections only from the exact Tailscale address to port 8443. With
Funnel enabled, `WEBAPP_PORT` must not be 8443. It can initiate connections only
to Hermes at `10.203.85.2:9120`; established replies are permitted. New connections
to the host/VM, LAN, Internet, DNS, or other stack services are blocked. IP
forwarding is denied. The startup process then switches to UID 10005 and removes
all effective, permitted, inheritable, ambient, and bounding capabilities before
executing HAProxy. Its temporary startup capabilities are not available to
HAProxy or its children. Operator-controlled Docker exec remains privileged.

HAProxy enforces exact Host authorities separately on local and Funnel paths.
It strips Forwarded and every X-Forwarded-* header, then sets scheme and peer
identity from the selected ingress path. Hermes trusts only the proxy's exact
backend IP. There is no fixed public_url, so native origin checks use the actual
host and trusted scheme. WebSockets, streaming responses and application headers
pass through. No additional body/storage/idle-time limits are introduced.
HAProxy warns about the intentionally infinite client/server timeouts at startup.

The native password throttle allows 10 attempts per 60 seconds per observed
client address and resets on process restart. Docker publication and Funnel can aggregate
visitors by ingress address, so this deployment does not claim independent
per-Internet-client throttling. Supplied client-address headers are discarded.

An authenticated webapp user is an administrator of the agent container. The
browser terminal runs there and can access agent state; it is separate from
model-generated terminal/Python execution over SSH. The browser file API is
backend-aware: workspace paths use SSH, while staged host-side files can remain
in the agent container. These UI capabilities must not be treated as executor
sandboxing. The executor has neither ingress network membership nor webapp or
Tailscale credentials and cannot connect to the private webapp paths.

## External content policy

Part 1 provides the safe default independently of the deferred streaming and
interactive work. See [verification and limits](#qualification)
for tested versions and acceptance evidence.

Set the root deployment `.env` value and apply it with `make up`:

```dotenv
WEBAPP_EXTERNAL_CONTENT=tor_proxied
```

| Mode | In-app behavior |
| --- | --- |
| `tor_proxied` | Default. Supported external raster images/icons load through the authenticated gateway over Tor. Unsupported content has a non-loading fallback and external link. |
| `ask` | No external image retrieval before load-once approval or a remembered Tor-image origin grant. Unsupported media/players/previews remain non-loading. |
| `off` | No external in-app loading or proxy retrieval, including previously approved images. In-app controls cannot override this ceiling. |
| `browser_native` | Explicit browser-native loading, using the browser connection. Native social preferences still apply. Existing authentication, main-script policy and preview sandboxes remain. |

Invalid or explicitly empty settings fail validation. An absent root setting
selects `tor_proxied`; missing/invalid gateway process settings refuse HTTP server
assembly. Native bootstrap captures the injected policy before profile dotenv
loading. Profile/model settings cannot relax it. The proxy checks its generated
mode marker before listening and sends a mode header checked by the gateway;
mismatch refuses access. `make up` renders configuration and recreates both
processes. Editing `.env` alone does not change running services.

Reload browser tabs after a mode change. New gateway policy applies to every new
image retrieval, including requests from stale pages. Previously delivered bytes
and browser document policies cannot be recalled. Close old `browser_native` tabs
and previews when switching to a private mode: their already delivered network
and script authority remains until they are closed/reloaded.

### Image approval and limits

The image placeholder names the destination origin and distinguishes **Load once
through Tor / retry**, **Remember this origin for Tor images**, and **Open externally
(uses your browser connection)**. Approval to retrieve a unique URL through Tor
can still reveal that someone viewed it; Tor protects the browser address, not
the fact of retrieval. Proxy failure displays its reason and never tries the
browser URL automatically. SVG and other unsupported responses keep the fallback.

Revoke remembered origins in **Settings → Appearance → Chat display → Image
permissions**. This surface stays available after images have loaded. Grants are
specific to Tor-image retrieval and exact browser/external origins. Localhost,
`127.0.0.1`, and Funnel have separate scopes. One deployment administrator shares
remembered grants between authenticated sessions on the same exact origin.
Logout and restart preserve them until explicit revocation. Load once persists
no grant or reusable credential. Revocation stops future retrieval, including
cached/repeated endpoint requests; already delivered bytes cannot be recalled.

The backend supports public IPv4 HTTP(S) PNG, JPEG, GIF, WebP, BMP and ICO, with
matching raster contents and media type. It pins a validated numeric address,
retains original Host and TLS identity, checks all redirect destinations and
never forwards browser credentials, cookies or referrers. In `ask`, a cross-origin
redirect is rejected before next-hop DNS/network activity, including load once.
Unsupported/private/IPv6-only destinations fail without a weaker fallback.
The native 25 MiB image limit is checked while streaming. Socket operations
allow 60 seconds for Tor latency; redirects are bounded. Responses are no-store
and there is no server image cache. The former CDN-only proxy route is removed.

### Local content, previews and links

Pasted/typed URLs retain Hermes's URL chips. Submitting a chip sends its
`@url:` reference text to the model, but this deployment does not automatically
fetch or attach the page, or append URL-extraction warnings. The model can use
explicit web research or terminal tools when asked to fetch it. File, folder,
Git and plugin context references retain native expansion and safety checks.
This backend policy also applies to CLI context expansion and is independent
of `WEBAPP_EXTERNAL_CONTENT`. Clicking a chip is a separate user action under
the preview policy below. Previously stored expanded content/warnings are not
rewritten or removed from conversation history.

Local/generated images and graphs keep authenticated native file paths. Local
media retains authenticated playback. A generated file hosted on a public CDN
is external even when the agent generated it. Shared Markdown, generated-result,
gallery, thumbnail and connector image renderers select private retrieval before
assigning a browser resource URL. Pet thumbnail rendering uses the same gate.
Browser-hosted link-title fetching is disabled and native favicon discovery
remains desktop-only.

In private modes, external audio/video, source/poster/subtitle/manifest dependencies
and social players do not load automatically. They have placeholders and ordinary
external links. Existing saved social permissions cannot bypass deployment policy.
Interactive media and in-app browser-native opt-in remain deferred to part 2.

The image disables the unsupported executor browser tools
`browser_cdp`, `browser_dialog` and `browser_vault` in every profile/content mode,
including `browser_native`; stale calls fail before a handler runs.
`computer_use` and `browser_exec` share `COMPUTER_USE_ENABLED`: off by default,
available only with their actual desktop executor SSH dependencies. See
[desktop configuration](configuration.md#optional-executor-desktop) and the
[qualification evidence](development.md#executor-desktop-qualification). Enabling
it grants no browser-tool or browser-preview permission. Its driver and desktop stay inside
the executor; gateway-local driver fallback and package installation are refused.

With the optional desktop enabled, the native Bot Screen APIs carry screenshots
and RFB pixels over authenticated same-origin connections and the existing SSH
stream. Viewing those pixels does not make the viewing browser fetch the desktop's
websites, and does not require `browser_native`. The separate browser interactive
terminal still runs in Hermes with administrative authority; a terminal opened
inside the executor's screen runs as runner in the executor.

Native takeover leases fence computer-use tools and viewer input, not arbitrary
code running as runner. Screens and browser profiles share the executor account.
Only entrust logins and other desktop state to an agent and operators allowed to
read them. A second viewer's takeover revokes the previous viewer's input; do not
rely on immediate closure of the previous watch connection across processes.

Cookie logout clears browser login cookies and blocks new authenticated HTTP
grants. Native already-open WebSockets and issued display tickets can outlive it;
display tickets remain single-use with a 30-second expiry. Closing the browser or
stopping the screen ends that viewing connection but does not revoke all existing
administrative RPC connections. To revoke access, stop the stack and apply
`make webapp-rotate` followed by `make up`, which reprovisions credentials and
recreates Hermes. Credential-file rotation alone is not applied to a running
gateway. This retains native authentication behavior without adding a parallel
session-revocation service.

The separate in-browser tools `desktop_preview`, `drive_preview` and
`annotate_preview` are available only when `WEBAPP_EXTERNAL_CONTENT=browser_native`.
Private modes omit all three from discovery and reject stale calls before a
handler or GUI callback. `browser_native` restores their native preview callbacks
without enabling executor browser or computer-use tools. The mode gate applies to the
whole preview tool, including file previews. Operators can still use the UI's
inert previews and interactive terminal; web extraction, x402_treazury research
and model SSH execution remain available.

Apply the rebuilt image with `make up` and start a new conversation to refresh
the model's advertised tools. Saved profiles cannot re-enable image-disabled
names or relax the captured deployment preview mode. This removes unsupported
tool entry points, not the authority of trusted administrator/plugin code.
Native-only `read_window_below` is also disabled in every mode: it requires OS
window access from the native desktop client and is unsupported in the webapp.
It is separate from the three browser-preview tools and their mode gate.

**Use `browser_native` only with Tor Browser or Brave Browser's Private Window
with Tor.** External previews use the viewing browser's connection, outside the
stack's Tor gateway. Ordinary Brave/private windows do not supply Tor routing.
The stack does not detect or verify the browser's routing, and these browser
configurations have not been qualified here. Brave's Tor windows lack many of
Tor Browser's anonymity protections; see [Brave's explanation](https://support.brave.app/hc/en-us/articles/360018121491-What-is-a-Private-Window-with-Tor-Connectivity).

Optional computer use and browser automation execute inside the SSH executor;
their qualification scope is recorded in the
[development guide](development.md#executor-desktop-qualification), including
[browser result checks](development.md#browser-harness-and-results). Browser screenshots are transferred
into generated gateway cache files for native vision/results. Downloads remain
executor workspace files, accessed through the existing authenticated file APIs.

HTML/plugin previews show inert source in private modes. Untrusted HTML is never
parsed or executed there, including nested frames, resource hints, workers,
WebRTC/STUN or script navigation. This is a deliberate fallback: CSP alone does
not confine arbitrary preview JavaScript. Locally rendered sanitized SVG and
Mermaid diagrams remain; external SVG references are blocked. Active HTML/SVG
file and plugin-asset responses are attachments with an inert sandbox policy,
including direct navigation/new tabs. The served preview shells retain their
native sandbox in `browser_native`; private shells only display source text.

Ordinary deliberate external links remain browser navigation. Downloads remain
available, but opening a downloaded document outside the webapp may contact
external services. Browser-native content and external navigation bypass Docker's
Tor gateway. The policy does not gate ordinary model inference or agent tool
requests, and does not protect against trusted administrator actions, installed
backend plugins with agent authority, host compromise or browser extensions.

The main app retains native bootstrap script hashes and unrelated script
restrictions. Private response policies restrict resource sources, allow only
same-origin APIs and exact-origin WebSockets, suppress referrers and disable DNS
prefetch. Every separately served active document is covered. These browser
controls do not change agent/executor networks or grant extra internal access.

The image has an empty agent-side `/workspace` to satisfy native browser session
cwd validation. It shares no mount or files with the SSH executor. Browser-terminal
files there are ephemeral across recreation; durable agent state belongs under
`/opt/data`. Model terminal/code execution and workspace file APIs continue using
the separate durable executor workspace.

### Qualification

The safe-default/passive-media implementation passed final independent review of
`3db58120e78f003d5b3402d34a4541e9fa39a6a7` against `078e0eb`, with no material
findings. Its integrated qualification covered 24 browser/mode/ingress cases;
the scope and practical limits are described below. Detailed historical plan
evidence remains in Git history. Streaming and interactive opt-in remain deferred.

`make images-test` uses public-numbered HTTP/TLS canaries on isolated Docker
networks, with no uplink or published ports. It qualifies socket destinations,
DNS changes, raster/size enforcement and native auth/consent. Stop other test or
deployment stacks first because inference/MCP fixture subnets are shared.
This destination fixture does not establish that its local fetches used Tor.

`make webapp-test` uses the built image, disposable native message/tool history,
SSH files, local media, controlled browser TCP/TLS canaries, and local/simulated
Funnel ingress. Its inference endpoint is a deterministic local fixture with no
uplink or provider calls; actual Teep routing is qualified separately by `make test`.
Browser image-success fixtures control the same-origin image API response; real
backend retrieval is independently exercised by `images-test` and the real Tor
image check. Direct Chromium NetLog observes canary DNS/TCP/preconnect activity;
a reserved `.invalid` positive-control lookup cannot select an HTTP endpoint.
No production wallets, paid calls or real Tailscale enrollment are used.

Install every browser used by this suite in the explicit test environment:

```sh
PLAYWRIGHT_BROWSERS_PATH=/tmp/private-hermes-content-browsers \
  /tmp/private-hermes-browser-tests/bin/python -m playwright install chromium firefox webkit
PLAYWRIGHT_BROWSERS_PATH=/tmp/private-hermes-content-browsers \
  WEBAPP_BROWSER_PYTHON=/tmp/private-hermes-browser-tests/bin/python make webapp-test
```

The qualified desktop engines are Chromium 156.0.8078.4, Firefox 157.0 and WebKit
27.2 on the tested arm64 target, with all four modes and both fixture ingress
paths. TCP/TLS canaries cover all three; direct DNS/preconnect NetLog observation
is Chromium-only. Other browsers/platforms are unqualified.
Fixture HTTPS is not live Funnel qualification. Tor image retrieval has separate
exit-control/transparent-route evidence; successful same-origin bytes alone
are not proof of Tor routing. Provider attestation and funded settlement remain
outside these browser checks.
